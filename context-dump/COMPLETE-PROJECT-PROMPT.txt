1. IDENTITY AND MISSION
--------------------------------------------------------------------------------
BugShield = "Multi-Agent Driven Intelligent Bug Detection and Secure Deployment
System". It is a CSE major project (BCS786, Team No 40, Sai Vidya Institute of
Technology, VTU) designed to be small, explainable and viva-defensible: every
claim is backed by a test, a benchmark row, or a live commit SHA.

Core loop (the whole point): a visitor on a client website clicks a widget and
reports a bug -> the BugShield dashboard receives it -> AI judges whether it is
a REAL defect by reading the client's actual source code -> if real, AI writes
a minimal fix -> the fix is verified with real tools -> it is committed to the
client's GitHub repo -> Render auto-redeploys -> the dashboard proves the fix is
live by reading the commit SHA from version.json.

Two separate websites, two GitHub repos, both on Render free tier:
  Dashboard + API: repo buildshield-re, live https://buildshield-re.onrender.com/
  Client demo shop: repo shop-re-test, live https://shop-re-test.onrender.com/
The demo shop is an Amazon-style storefront ("amazin") with 17 planted bugs;
answer keys (PLANTED_BUGS.md, all-bug.md) exist only locally and are gitignored.

4. PIPELINE AND THE 9 AGENTS
--------------------------------------------------------------------------------
State machine statuses: RECEIVED, DEDUPLICATED, TRIAGING, ANALYZING,
INVALID_REPORT, NOT_REPRODUCIBLE_IN_CODE, SOURCE_UNAVAILABLE, AI_UNAVAILABLE,
PATCHING, PATCH_FAILED, VALIDATING, VALIDATION_FAILED, AWAITING_APPROVAL,
REJECTED_BY_ADMIN, APPROVED, PUSHING, DEPLOYING, RESOLVED_AND_DEPLOYED,
DEPLOY_TIMEOUT, ROLLED_BACK, FAILED. UI groups them into Received /
Investigating / Fixing / Needs you / Shipping / Fixed & live / Closed / Stuck.

Order: Intake -> Localizer -> Analyzer -> Risk -> Patcher -> Critic -> Validator
-> [approval gate] -> Deployer -> Verifier. Every stage writes a pipeline_step
row and broadcasts over WebSocket; stages are idempotent and resumable after
restart (stuck jobs re-queued on boot).

  1. INTAKE: strip HTML, cap lengths, fingerprint (key+title+page path+first
     error, 10-min dedup window -> occurrences++), extract quoted strings,
     selectors, stack file:line, URLs, identifiers.
  2. LOCALIZER: repo map (ignores node_modules/dist/locks/>200KB); cheap grep
     first (e.g. typo "Shoping" found without LLM), stack-trace file names,
     page-URL mapping; rank top 8; LLM selects <=5 files that MUST exist;
     read +-80 line windows.
  3. ANALYZER: strict JSON {is_defect, confidence, defect_type (14 classes),
     file, lines, explanation, impact}; confidence <0.5 or is_defect=false ->
     INVALID_REPORT with the reason shown to admin.
  4. RISK: deterministic 0-100: base 25; defect-type weights (security +25,
     typo_copy -5); sensitive path +15/+8 capped +35; money/checkout +20 AND
     human gate; size +0..12; low confidence +6. >=70 = CRITICAL.
  5. PATCHER: search/replace edits only, each must match EXACTLY ONE location,
     <=3 files, <=5 edits/file, <=40 changed lines, forbidden paths blocked,
     real unified diff, one strict re-prompt on failure.
  6. CRITIC + SAFETY: second LLM approve|concern|reject plus deterministic
     scanner on ADDED lines (scripts, URLs, eval, innerHTML, network calls,
     base64, credentials, obfuscation, report-instruction echo).
  7. VALIDATOR: registry by extension — js (node --check), ts/tsx/jsx, json,
     html, css, yaml, python (py_compile), php -l, ruby -c, gofmt, generic
     sanity. Missing runtime -> NOT_PERFORMED with reason (never green).
     Project tests are NOT auto-run (no dep installs, no secrets to scripts).
  8. DEPLOYER: drift re-check, ONE atomic multi-file commit via Git Data API
     (ref -> commit -> blobs -> tree -> commit -> ref PATCH), message
     "fix(bugshield): <summary> [ISSUE-id]" with risk/validators/approver;
     non-fast-forward -> rebase once; per-site mutex.
  9. VERIFIER: poll version.json every 10s up to 10 min for the pushed SHA;
     no marker -> UNVERIFIED; 3 health probes need 2xx; failed post-deploy
     health -> automatic revert commit -> ROLLED_BACK.

Approval gate triggers: score >= threshold, security-sensitive, per-site
always-approve, autoDeploy disabled, safety hit, critic concern, validation not
clean, oversized diff. Scope rule in every prompt: fix ONLY the reported
defect; ignore other bugs noticed in the code.

5. API, SECURITY, DATA MODEL
--------------------------------------------------------------------------------
API: GET /api/health; POST /api/v1/issues (public, CORS * for POST+OPTIONS);
/auth/login|logout|/me; /api/websites CRUD + /test + /keys; /api/issues list
(cursor pagination) + :id + approve|reject|retry|revert; /api/settings/policy
+ integrations-status; /api/audit; /api/stats/overview; /api/members; WS /ws.
Uniform JSON errors; CSRF header X-Requested-With + Origin/Host on mutations.

Ingestion guards in order: 256KB cap (413) -> key hash (401) -> origin
allow-list (403) -> 30/min/key and 60/min/IP with Retry-After (429) ->
validation -> 10-min dedup -> store -> async enqueue. Caps: title 300,
description 4000, steps 2000, outerHTML 2000, text 500, errors 20 (stack
8000), console 50, network 20 (URL+status only). No passwords/input values.

Security: scrypt passwords N=16384 min 12 chars, 256-bit sessions hashed at
rest 12h TTL, HttpOnly SameSite=Strict cookies, login lockout, central redactor
for tokens/keys, keys stored hashed and shown once, HS256-free opaque tokens,
role gates (owner/admin/reviewer/viewer), nightly backups on SQLite path.

DB (15 tables): users, sessions, websites, ingestion_keys, issues,
issue_cases, pipeline_steps, patches, validation_runs, approvals, deployments,
settings, audit_log, jobs, _migrations. Dual backend via DATABASE_URL:
schema.sql (SQLite AUTOINCREMENT, dev/test) and schema.pg.sql (Postgres
SERIAL, production). `?` placeholders rewritten to `$n`; insertGetId uses
RETURNING on pg. Fail-fast if production boots without DATABASE_URL.
